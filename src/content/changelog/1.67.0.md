#### Changed

- An advisory for software in a build-only Dockerfile stage is reported at
  info. A multi-stage build publishes its final stage; an image named by an
  earlier `FROM` reaches it only if the final stage is built on that stage or
  copies system files out of it (`COPY --from` of `/`, `/usr`, `/lib`, `/etc`,
  `/var`, `/opt` and the like). A builder that only hands over a binary is a
  build environment, and its packages were rated as if they shipped: nox's own
  `golang:1.27-alpine` builder made a zlib advisory gate a scan whose image
  holds no zlib. Such a finding keeps its rating in `original_severity`, says
  `severity_source: build_stage_only`, names the stage in `image_stage`, and
  says what building with `--target` that stage would mean. A `FROM` or
  `COPY --from` naming a variable counts every stage as shipped. See
  `docs/adr/0004-build-stage-image-advisories-are-info.md`.

#### Fixed

- The ISO 27001 report said, under A.8.28 Secure coding, that the scan outputs
  did not show any application code was present, in the same section that cited
  an authorization lead found in that code: `findings.json` did not record the
  source files a scan read. It now does, by language, in `meta.source_files`,
  and the code and cryptography checks read their subject from it.
- `nox fix apply` installed packages to move a version, so in a project with
  no `node_modules` it created one, and the next `nox scan` reported a critical
  and two high "secrets" from third-party READMEs and type definitions inside
  it. Where there is no `node_modules`, npm and pnpm now rewrite only
  `package.json` and the lockfile (`--package-lock-only`, `--lockfile-only`);
  an existing one is still kept in step. bun has no lockfile-only update and
  still installs.
- With `advisories.policy: prepare`, `nox advisories` said "prepared as a pull
  request" for a transitive npm package whose parent pins it below the fix.
  `nox fix` holds that move, so the remediation action opened no pull request,
  while the job summary and issue promised one. The decision now reads the
  same lockfile `nox fix` reads and says the upgrade is not prepared, which
  parent holds it, and the `overrides` entry that would force it. The MCP
  `advisories` tool makes the same check.
- A PR-scoped scan (`--changed-since`) reported an import as SLOP-001,
  undeclared, whenever the manifest declaring it was not among the changed
  files: what a project declares was read from the diff, not the tree. On
  nox's own PR #1082, editing `safe.py`'s flask import flagged flask beside the
  `requirements.txt` naming it. Declarations, path aliases and first-party
  modules are now read from the whole tree; findings are still reported only
  on changed files.
- A SARIF report with no findings wrote `"rules": null`, which SARIF 2.1.0
  forbids; GitHub rejected the upload, and the alerts of the previous scan
  stayed open. Found when the fix above left nox's own PR-scoped scan with
  nothing to report. `rules` is now always an array.
- OpenTelemetry 1.47.0 (GHSA-q7gw-24fr-5p69: `AttributeValueLengthLimit` is
  bypassed by values made of U+FFFD runes), linked through the MCP server.
- `examples/ai-app/safe.py`, the fixed half of the AI example, returned the
  model's answer from a Flask view as a string, which Flask serves as HTML: an
  XSS through the model's output. It returns JSON.
