#### Added

- IAC-507 reports a release workflow that restores a cache another workflow can
  write: the cross-workflow cache poisoning of the May 2026 TanStack compromise,
  which IAC-506 cannot see because the two halves are in different files. The
  writer runs on `pull_request_target`, `workflow_run` or `issue_comment`, checks
  out the pull request's commit (IAC-505's test) and saves a cache
  (`actions/cache`, `actions/cache/save`, or a setup action's `cache:` input).
  The restorer is a step of a job that can publish (`id-token: write`,
  `npm`/`pnpm`/`yarn publish`, `twine upload`, `goreleaser`, a publishing secret
  such as `NPM_TOKEN`), or of a job one that does needs, and its key or
  `restore-keys` can meet the writer's; `${{ }}` expressions are treated as
  wildcards and the message says what matched. The finding is on the restore step
  and names the writer's file and line. Plain `pull_request` is not a writer: its
  caches belong to the merge ref. GitHub now gives `pull_request_target`,
  `workflow_run` and `issue_comment` runs read-only cache access unless the
  workflow or job sets `cache-mode: write` or `write-only`: a writer that does is
  high confidence, one that does not is low confidence and the message says so,
  and `cache-mode: read` or `none` is not a writer. It needs every workflow of
  the scan, so `nox scan` reports it and a single-file call (MCP, LSP) does not.
  A job that runs only for the repository's own pull requests, a dependency bot
  or merged ones is not a writer, `id-token: write` alone is not a publish, and
  `setup-go` before v4 has no cache. Measured on 320 repositories, 14 report it.
- A PyPI dependency finding climbs on the functions NOX Intelligence's analysis of the fix lists as changed, as npm findings have since 1.65.0. Project source that references one (`from PIL import Image` then `Image.open(...)`, `import yaml` then `yaml.load(...)`, `from a.b import f` then `f(...)`, attribute chains, and `Class.method` called through its class) raises the finding to a call path with the site as its witness, labelled `affected_symbol_evidence: source_reference`. Tests, `conftest.py`, comments, strings, relative and star imports are not read as uses. A miss lowers nothing.
- A PyPI distribution imported under another name is recognised when the analysis of its own files names the module: Pillow as `PIL`, PyJWT as `jwt`. The finding records them in `import_names`, the import climbs to `symbol_used`, and the source call graph's climb to `call_reachable` asks for calls into those modules too. In the npm/PyPI re-measure, 394 undecided `pillow` findings were in repositories whose own source imports `PIL`, which nox matched against the name `pillow` and missed (the other 295 were in repositories that do not import it). This needs NOX Intelligence to place PyPI symbols in modules (nox-intelligence #187); until it does, nothing changes.

- `MCP-027` reports a hidden instruction in the description of a tool an MCP
  server registers (tool poisoning, OWASP MCP03): an order to keep something
  from the user ("do not mention this to the user"), to read another tool's
  config (`~/.cursor/mcp.json`) or a credential and pass it on, or to disregard
  prior instructions. It reads Python `@mcp.tool`/`@server.tool` docstrings and
  `description=` keywords, and TypeScript/JavaScript `server.tool(name,
  "...")`, `registerTool(name, {description})` and `tools: [{name,
  description}]` lists, in files that import an MCP server library
  (`mcp`, `fastmcp`, `@modelcontextprotocol/*`). A docstring of a function that
  is not a tool, a comment, a string in another role and a file that defines no
  tool are not reported. The poisoned `add` tool of the public demonstration
  produced no finding before; `MCP-009`/`010`/`011` could not see it, because a
  match inside a string over 96 bytes is dropped as a data blob and a payload
  is always that long. Ten public MCP server repositories give no hit. The
  directive patterns are shared with `AGENT-001` and `AGENT-004` rather than
  copied, so the three cannot drift.
- IAC-505 reports a workflow that runs on `pull_request_target` or `workflow_run`
  and checks out the pull request's own commit (a "pwn request"), through
  `actions/checkout` or a reusable workflow given that ref. A job whose `if:`
  keeps it off those triggers is not reported, nor is a `ref:` that only an
  action reading check status receives.
- IAC-506 reports a cache saved in such a job (`actions/cache`,
  `actions/cache/save`, or a setup action's `cache:` input): it is saved in the
  base branch's scope, where a release workflow restores it, the shape of the
  May 2026 TanStack compromise.

#### Fixed

- An opted-in scan now says what it contributed. With `scan.intelligence.contribute` on, every scan sent its observations (and, with `scan.intelligence.outcomes`, its outcome report) to NOX Intelligence without a `[network]` line, while the dependency-lookup line beside it said "findings were not sent". A `[network] contribution:` line now counts the observations and the outcome report's findings, names the endpoint and how to opt out, and the lookup line speaks only for the lookup. Verified end to end against a local NOX Intelligence: the counts printed match what the service received.

- An online scan of an npm workspace whose `package-lock.json` lists a member
  under a short directory (argotorg/sourcify's `ui`) panicked while building
  dependency remediation advice (`slice bounds out of range [12:2]` in
  `npmtree`) and wrote no report. A workspace member is keyed by its directory,
  not a `node_modules/` path; its name now comes from the entry's `name`.
  Longer member keys did not crash but were read under a wrong name
  (`packages/lib-sourcify` as `-sourcify`).
- `MCP-009`, `MCP-010` and `MCP-011` never saw a payload in a real tool
  description. They claim "MCP tool metadata contains ...", but a match inside a
  string over 96 bytes is dropped as a data blob, and a poisoned docstring or
  `description` literal is always that long, so only the short, easy payload
  was reported. They now keep a match that lies in the description of a tool
  registered by an MCP server (the structural test `MCP-027` already uses,
  extended to Go's `mcp.WithDescription(...)` and the `mark3labs/mcp-go` and
  `modelcontextprotocol/go-sdk` imports), and still drop every other long string
  and every comment. `MCP-010` also missed "Do not mention this to the user",
  the phrase the public tool-poisoning demonstrations use: its keyword prefilter
  listed four of the eight verbs its pattern accepts, so the pattern never ran.
  On the ten public MCP repositories used for `MCP-027` the only new finding is
  a true positive in `cisco-ai-defense/mcp-scanner`'s eval corpus; on that
  project's example malicious servers the three rules go from 1 finding to 6.
  `MCP-027` stays: its vocabulary is broader and it reports once per description.
- IAC-011 missed `pull_request_target` written in the scalar, list or sequence
  form of `on:` (`on: pull_request_target`, `on: [push, pull_request_target]`),
  because its pattern required a colon after the event. It now reads the
  workflow's triggers, reports once per workflow at the trigger, and no longer
  fires on a comment or an `event_name` check in a workflow that does not run
  on it. Measured on the workflows of 20 large repositories: two workflows newly
  reported (withastro/astro), none lost.
